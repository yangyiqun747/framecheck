# 可选串口验收入口（0.3.1）

`serial-run` 把每个项目自己的发送内容、预期回包和观察窗口带到真实串口。它适合逐条发送、收到结果后再继续的测试；不适用于未经适配的持续遥测流，也不负责识别或烧录板端固件。

在 Codex 中可以说：“用 FrameCheck 根据这个项目的已确认规则准备串口验收，先展示测试行为，再执行。”插件先读代码和协议依据，只追问缺失规则，自己准备配置和用例。用户不需要手写 JSON。

## 两种明确选择的模式

```console
python scripts/framecheck_cli.py serial-run --dry-run --profile examples/serial/profile.json --suite examples/serial/suite.json --out ../serial-self-check
```

离线模式只给测试工具提供预先编排的回包，验证 I/O 流程。**它不运行用户解析器，也不连接板子。** 示例是另一个虚构二进制协议，不含 CRLF、不要求原样回包，不能直接作为用户设备的协议依据。

真实模式需要独立工具 Python 中的可选 `serial` 依赖。可创建虚拟环境并安装 `"<FrameCheck源码目录>[serial]"`；已有 `board` 环境也包含 pySerial。避免修改全局环境。随后使用该环境的 Python：

```console
python scripts/framecheck_cli.py serial-run --live --port <确认的串口> --profile <项目配置.json> --suite <项目用例.json> --out <新的报告目录>
```

两种模式均必须显式提供配置和用例，真实模式必须给出端口。输出目录必须为空，不覆盖旧报告。命令不自动枚举或选择端口、不下载依赖、不请求复位、暂停、解锁或烧录。它打开串口并发送用例中的内容；项目须已确认测试报文的用途。

## 项目配置

参考 [二进制示例配置](../examples/serial/profile.json)。`schema_version` 为 1，字段如下：

| 字段 | 含义 |
| --- | --- |
| `serial` | baudrate、bytesize、parity、stopbits，以及布尔 xonxoff/rtscts/dsrdtr；从工程与接线确认 |
| `ready_policy` | required 必须等启动标记；optional 在有界等待后可继续；skip 明确跳过启动标记 |
| `ready_banner_hex` | 预期启动标记；required/optional 模式不可为空 |
| `ready_timeout_s` | 等启动标记的时间上限 |
| `response_timeout_s` | 发送队列清空后，等待回包及其静默窗口的上限 |
| `quiet_s` | 完整回包后继续观察无额外字节，必须小于 response_timeout_s |
| `write_timeout_s` | 单次写入超时；随后等待驱动发送队列清空也受此上限约束 |
| `inter_chunk_s` | 一条交互内，相邻发送分块之间的间隔，可为 0 |
| `ready_prompt` | 可选的等待提示；属于项目数据，不是代理指令 |

`--ready-policy` 可显式覆盖配置，覆盖后的配置仍会校验并记录指纹。没有启动提示的协议可明确选择 skip；如果原协议要求同步，不应为绕过失败而改成 skip。工具不替用户复位，自动复位属于另行授权的项目辅助流程。

时间参数上限为 60 秒；除分块间隔外均需大于 0。资源上限为每个 JSON 2 MiB、每套 256 个用例、2048 次交互、每次期望回包 65536 字节，波特率配置范围 1..4000000。这些是工具资源限制，不是协议载荷上限或硬件能力保证。底层驱动调用仍可能有平台限制；本版没有整轮子进程看门狗。

## 项目用例

参考 [示例用例](../examples/serial/suite.json)。顶层为 `schema_version: 1` 和非空 `cases`；每条 case 有唯一 `id` 和非空 `transactions`。每次交互包含：

- `chunks_hex`：按顺序发送的非空字节分块列表。
- `expected_hex`：预期完整线上回包，逐字节比较；可以与发送内容完全不同。
- `expect_silence_s`：只有期望回包为空时才能提供，而且必须明确给出正数观察窗口。

合法报文没有回包若只是“没有实现发送”，不能自动认定解析器正确。预期应由独立协议依据和已确认板端行为支持。

## 失败与报告

生成 `report.json` 和 `report.md`，保存模式、启动状态、用例/交互结果、请求分块、原始回包、事件时间、配置/用例/工具源码指纹。`is_board_validation` 表示进入真实交互路径，不表示全部通过；应同时检查 verdict、counts 和 close_error。端口打不开时不会声称已验收板子。

执行遇到第一处错误或回包不符即停止，后续用例标为 skipped。发送前发现未归属的旧字节会保存并失败，不清空后继续假装通过。普通回包缺失是 error；与预期字节不同是 fail；明确要求静默时收到任何字节也是 fail。关闭串口失败会把整轮结论改为未通过。

退出码：通过为 0；执行未通过为 1；配置或准备失败为 2。解析命令配置失败也可能直接显示帮助。板端失败目前保存完整交互记录，不自动生成独立最小重现；有状态用例需连同前置步骤重放，不能直接套用宿主 `replay`。

## 验证范围

静默断言是有限时间观察，不代表永远无输出。观察从驱动报告发送队列清空后开始；驱动计数不等于所有位已经到达 MCU。USB 和驱动可能合并分块，主机请求的分块及间隔也不保证与 MCU 中断边界一致。

代码在打开端口前设置 DTR/RTS 为低，不通过它们请求复位；设备驱动在打开时仍可能产生线状态变化。硬件流控以项目配置为准。长期压力、无间隔连续发送、随机模糊测试、DMA/中断极限及完整电气时序尚不在本入口的验收承诺内。
