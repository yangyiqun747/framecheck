# 协议与用例

FrameCheck 对照显式预期消息检查解析器。内置帧格式用于公开演示；真实产品协议通过自己的适配器和 `--suite` 接入。

## 示例协议 v1

```text
AA 55 | len:u8 | seq:u8 | type:u8 | payload:len | CRC16:little-endian
```

| 字段 | 规则 |
| --- | --- |
| 帧头 | 固定两个字节 `AA 55` |
| `len` | 负载字节数，允许 `0..64` |
| `seq` | 8 位无符号序号，解析器只原样输出 |
| `type` | 8 位无符号消息类型 |
| `payload` | `len` 个任意字节，允许包含 `AA 55` |
| CRC | CRC-16/CCITT-FALSE，覆盖 `len` 到负载末尾，低字节先传 |

总帧长为 `len + 7` 字节。CRC 参数：多项式 `0x1021`，初值 `0xFFFF`，输入和输出均不反射，最终异或值为 `0`。标准校验输入 ASCII `123456789` 的 CRC 应为 `0x29B1`。

示例解析器输出：

```json
{"seq": 1, "type": 16, "payload_hex": "102030"}
```

`payload_hex` 是小写十六进制字符串，不含空格。这是示例适配器的约定；框架不要求其他协议使用同样字段。

## 分包与恢复规则

1. 不完整候选帧保留到下一次输入；不会提前输出消息。
2. 无帧头的噪声丢弃，但保留末尾单个 `AA`，以便下一块以 `55` 开头。
3. 长度超出范围或完整候选帧 CRC 错误时，丢弃候选起点的一个字节，然后重新搜索帧头。
4. 完整有效帧输出一次，再继续解析缓存中的后续帧。
5. 有效帧的负载不因为包含帧头而被拆开。

这些恢复规则是示例协议的明确约定。真实协议可能采用其他策略，需要相应修改预期。若候选头声明的长度有效但数据不完整，示例会继续等待；不会仅凭后面出现帧头就判定前一帧无效。用例因此不会对这种模糊情况假定任意恢复结果。

同一字节流的分块测试保持字节内容与顺序一致。用例没有模拟接收间隔，不验收实际串口超时。

## 自定义用例格式

JSON 文件使用 UTF-8；顶层 `schema_version` 为 `1`。下面是一个自定义 ASCII 行协议的完整用例，与上面的二进制示例协议无关：

```json
{
  "schema_version": 1,
  "name": "行协议分包回归",
  "seed": 0,
  "protocol": {
    "name": "ascii-line-v1",
    "description": "以 LF 结束，输出不含 LF 的 ASCII 行"
  },
  "cases": [
    {
      "id": "split-ok",
      "title": "OK 在两次接收后完整输出",
      "category": "fragment",
      "chunks_hex": ["4f", "4b0a"],
      "expected": [{"line": "OK"}]
    }
  ]
}
```

`chunks_hex` 中每一项代表一次 `feed(bytes)` 调用，顺序保留。允许用空字符串表示空输入。每个用例开始时创建解析器并调用 `reset()`；不同用例之间不共享解析状态。

`expected` 是按发出顺序排列的 JSON 对象列表。框架汇总该用例所有 `feed()` 的输出，再比较列表、消息字段和值；不会忽略多余字段，也不会按序号重排。JSON 对象的键顺序不影响比较。布尔值、数字、字符串、空值等 JSON 类型必须一致；数字 `1` 和 `1.0` 按相等数值处理，布尔值 `true` 与数字 `1` 不相等。NaN 和 Infinity 不是合法用例值。

当前不断言某条消息在第几次 `feed()` 发出；它检查整段用例结束后的消息序列。若需要验收实时输出时机，应扩展用例契约后单独测试。

用例约束：

- `id` 唯一，包含 1 到 80 个 ASCII 字母、数字、下划线或连字符。
- `cases` 包含 1 到 2000 个用例。
- 每个 `chunks_hex` 包含 1 到 10000 项，均为可解码的十六进制字符串。
- 整套用例的输入字节不超过 4 MiB，输入 JSON 文件不超过 16 MiB。
- `title`、`category` 可省略；`name`、`seed`、`protocol` 也有默认值，建议填写以便复核。

## 建立可信的预期

先确认协议的大小端、字段范围、CRC 覆盖范围、异常帧处理和重同步策略。至少准备一条已知正确报文、一条坏报文，以及它们各自应该输出的消息。

预期结果必须独立于待测实现。可以依据协议手工构造，使用设备供应方公开的校验向量，或由另一种实现独立生成并人工检查。若把待测解析器的输出直接写进 `expected`，测试可能重复证明同一个错误。

固定种子的内置随机用例通过已知字段构造报文和预期消息；随机性仅用于载荷和切块覆盖。相同种子可重新生成相同用例，但报告运行 ID、时间和耗时会变化。失败文件直接保存实际分块，重放不依赖重新生成随机数。

## 失败文件

`repros/<id>.json` 本身包含一条可运行的 suite，用 `cases` 保存原始输入和预期。额外的 `observed` 保存原运行的状态、实际消息和原因；`original_adapter` 保存原解析器说明及指纹。

重放以当前明确指定的解析器运行，不把旧的实际消息当作预期，也不自动执行文件中记录的路径。因此同一份失败用例可分别验收修复前和修复后的实现。
