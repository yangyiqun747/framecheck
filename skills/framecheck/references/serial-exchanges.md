# Project-specific serial exchanges

Use for ordered request/response checks on an explicitly selected port. It is optional and separate from host parser regression and board metadata. Unsolicited continuous telemetry is outside this mode.

- Read the relevant project, supported command meanings, expected wire responses and startup behavior. Use independent specification or user-confirmed examples. Do not assume echo, CRLF, 199 bytes, UART pins, board type, port or baud rate. Do not probe unknown commands to guess a protocol.
- Prepare a profile and suite in the user's test workspace. Follow [serial format](../../../docs/serial-exchanges.md). The user reviews a short rule summary; ask only for missing facts. Reuse prior authorization and confirmed choices. Readiness may be required, optional or explicitly skipped; do not weaken it just to make a failed run pass. An empty readiness marker cannot be used with required/optional mode.
- Run `serial-run --dry-run --profile <profile> --suite <suite> --out <new-dir>` first. This feeds scripted replies to the runner and does not execute any parser or communicate with hardware. Never report it as board acceptance.
- For authorized real communication, use a trusted Python with the optional `serial` dependency and `serial-run --live --port <confirmed-port> --profile <profile> --suite <suite> --out <new-dir>`. Ports are not auto-selected. Confirm the active firmware through existing project evidence or the user's setup; the generic runner does not identify firmware. Preserve the original firmware/source. This tool does not reset, halt, unlock or flash. Keep any separately authorized project reset/flash helper outside this generic mode.
- Inspect every failure/error, readiness status, skipped case, original chunks, received bytes and events in `report.json`. Unexpected queued input fails before the next write instead of being flushed into apparent success. Missing expected replies, incomplete writes, driver-queue timeout and close failure never count as successful robustness checks. Stop after the first mismatch/I/O error; preserve the report and expected behavior.
- State the tested scope: exact response bytes and bounded silence/quiet windows under the selected pacing. A driver queue becoming empty does not prove electrical completion. USB/driver buffering can merge writes; requested chunk boundaries and delays are not guaranteed MCU callback boundaries. No stress, DMA, timing or complete correctness claim follows from these fixtures.

Reports fingerprint the profile, original suite, effective readiness override and runner source. This mode records full exchanges but does not create standalone minimized failures or guarantee independent replay of stateful cases; host `replay` remains a different command.
